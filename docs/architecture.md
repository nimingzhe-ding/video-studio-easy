# 服务端架构

## 请求、身份与归属

Vue 页面与 API 同源提供。Spring Security 保护 /api/** 和 /ws/**，Redis 持久保存登录会话。登录使用 BCrypt 验证密码并轮换会话 ID；写请求必须携带 CSRF Header。注册默认关闭，首次部署使用环境变量创建管理员。

media_asset.owner_id 是资源归属的依据。素材列表按用户查询；所有任务、报告、下载、SSE 与证据帧入口都核对归属。提交任务时也校验请求体中的 assetId。未归属的旧数据不会自动开放给任意账户。

## 分析链路

上传原件与分片 → S3；素材元数据 → MySQL。

提交任务 → MySQL 事务写 analysis_job 与 job_outbox → 发件箱轮询 → RocketMQ 确认投递 → 消费者执行。

消费阶段：从 S3 取工作副本 → FFmpeg 音频切片与关键帧 → 云端 ASR 与 Tesseract OCR → 时间轴证据 → 分块摘要与 Embedding → Qdrant 索引 → Planner / Executor / Critic → 确定性证据校验 → Markdown / Word / 字幕。

关键帧、原件和 Word 持久化到 S3，转写、事件、分块和 Markdown 持久化到 MySQL。Redis Pub/Sub 只负责唤醒 SSE；事件历史以 MySQL 为准。

## 可靠性边界

- 发件箱和任务同事务，消息发送失败不会丢失已接受的任务。
- 发件箱发送成功但数据库提交失败时可能再次发送，消费者必须幂等。
- 发件箱投递分三段执行，**不是**一个长事务：短事务里 `FOR UPDATE SKIP LOCKED` 领取一批记录并立刻把 `next_attempt_at` 推出租期后提交；发送在事务外进行；成功写 SENT、失败写退避时间。原因是 RocketMQ 的 `syncSend` 在 Broker 卡顿时会一直阻塞到超时（5 秒），一次取 10 条最坏持锁 50 秒，既挡住其它实例也拖住连接池。用「租期字段」而不是新增 SENDING 状态，是为了让「进程在领取后崩溃」这条路径自动恢复：租期一过记录重新可领。
- 消费者以 Redisson 自动续期锁阻止并发执行，成功任务与旧代次消息直接确认。
- 暂时故障由 RocketMQ 自动重试最多三次；耗尽后落 failed_delivery，原消息由 Broker 留在 %DLQ%video-studio-workers。永久业务错误、模型请求被拒绝和本地预算耗尽直接写失败台账后确认，等待修复后人工重投。上游 HTTP 429 仍作为限流故障有限重试。
- 人工重试递增 generation，旧代次消息不能启动新的分析。
- 重复投递撞上 RUNNING 任务时直接确认，不消耗重投次数；PENDING / FAILED 任务遇到锁冲突会重投，耗尽时条件更新为 FAILED 并写台账，避免永久停在 PENDING；若持有者已经消失，任务停在 RUNNING，由回收器按「15 分钟无进度 + 抢锁成功」重新排队并从断点继续，自动重跑上限为 3 次。回收动作的「改状态」与「写发件箱」在同一事务里：只改状态不写发件箱，任务会永远停在 PENDING 而没有任何消息来驱动它（发件箱轮询不会补偿这类记录）。
- 任务取消以数据库状态为准，在后续阶段或进度检查点停止。正在进行的远程请求可能要等当前调用返回。
- 不承诺外部模型计费恰好一次。模型调用完成后进程退出，恢复时可能重复请求。
- 断点记录阶段与复用证据，不恢复半次外部模型请求。

## 失败策略

不生成替代报告，不把数据库或模型错误转换成“成功”。向量服务运行期故障允许受控降级，成功任务带 degraded 标记。模型缺失凭证时启动失败；网络故障进行有限重试，耗尽后任务失败。Critic 缺失或证据未通过时不发布成功报告。Qdrant 维度不符时拒绝启动，不删除现有集合。

**正常优先完整检索，异常才降级**：每次检索先请求 Qdrant，失败后重试一次。仍失败时，优先用 MySQL 中完整、合法且维度匹配的已保存向量做余弦相似度检索；历史向量不完整时才使用关键词和画面文字匹配，没有命中则明确失败，不随意挑选无关证据。模型 Embedding、Planner / Executor / Critic 与证据校验仍正常执行；向量维度或数值错误直接失败。

向量索引写入故障会告警；实际检索降级会写 warn 事件、任务 degraded 标记、Markdown / Word 报告说明、追问回答说明和指标。下一次检索重新尝试 Qdrant，恢复后自然回到正常路径。`RETRIEVAL_FALLBACK_ENABLED=false` 可关闭运行期检索降级，重试耗尽后直接失败；启动时的 Qdrant 连接与维度检查始终保留。

FFmpeg、Tesseract 是服务端真实处理工具；本地临时文件仅供计算。场景检测的固定采样兜底属于抽帧策略，不会替代语义分析。

## 存储清理一致性

`storage_cleanup` 与元数据在同一 MySQL 事务写入。领取清理项使用短事务与 `FOR UPDATE SKIP LOCKED`，设置 300 秒租期及随机令牌；S3 / Qdrant 删除在事务外执行，成功标记 DONE，失败保留 PENDING 并退避重试。领取者退出后租期到期可恢复，完成更新必须匹配令牌，旧领取者不能覆盖新领取结果。外部删除需保持幂等。

上传合并提交后才清理分片；取消和超时回收也使用清理队列。分片清理与上传共用分布式锁，遇到复用的上传 ID 时核对当前会话的 asset_id，避免旧清理项删除新会话的分片。本地工作副本在提交后尽力删除，不承担持久数据职责。后台清理可能存在延迟，监控 PENDING 积压、最老年龄与 attempts；DONE 历史可按运维保留策略归档。

## 部署与运维

MySQL 管理业务与发件箱；Redis 管理会话、锁、限流和累计配额；RocketMQ 管理任务投递；S3 管理二进制文件；Qdrant 管理向量索引。没有重复建设第二套持久存储。

配额分三层：单任务、全站每日、**单用户每日**。用户维度按任务归属反查（消费线程里没有 SecurityContext），额度用尽只挡住超额的那个人，而不是让全站一起提交不了任务。查不到归属的历史数据只受全站额度约束。

失败投递有独立的运维面：管理员可以列出 failed_delivery 里的记录并重投。重投走的是「递增 generation + 写发件箱」，与用户重试同一条状态机；原消息不重放，因为它带着旧代次。同一条记录只能重投一次，防止反复点按钮把费用放大。

异常消息必须先审计后确认：消息体严格校验单个 JSON 对象、重复键、ID 类型与范围，最大 64 KiB。无法解析或缺失有效任务代次的消息以 INVALID_MESSAGE 写入 failed_delivery，job_id / generation 使用 0 占位，只保存消息标识、固定错误说明和 payload_sha256，拒绝重投成任务。管理员排查发送方后可以标记 resolved_at / resolved_by；审计库不可用时抛错交回 Broker 重试。

诊断信息在截断前脱敏：任务错误、告警、事件和 API 错误屏蔽 Bearer / Basic、常见 Key / token / password 字段、sk- 格式 Key、URL 用户凭证和签名查询参数。任务与事件读取时也屏蔽历史诊断文本；控制台 Logback 编码器同时屏蔽格式化消息、原因链及 suppressed 异常，并保留堆栈。业务原文与报告正文不做通用文本替换；已存文件不自动重写。

Flyway 独占数据库结构迁移。Readiness 检查 MySQL、Redis、对象存储和 Qdrant。Prometheus 指标端点需要管理员身份；正式监控接入应通过私有网关或独立受保护的抓取入口。

离线回归评测直接复用实际检索排序和确定性证据校验，固定返回值替代外部模型 / Qdrant，不产生费用，CI 保存逐样例报告。它用于回归门禁，不宣称衡量真实模型质量，见 [评测说明](evaluation.md)。

现有 Word 插图、字幕时间轴校正、说话人音高聚类和多轮补证算法继续使用。说话人分离是基于音高的近似标注，应结合原片核对，不等同于声纹身份识别。

## 分析模式

分析模式是配置而不是代码：`modes.json` 定义 code、label、guidance、必需小节与默认目标，外置文件可通过 `agent.modes-file` 覆盖或追加。新增一种模式（比如「合同审查」）只需加一份配置和对应的提示词，不改 Java、不重新打包。

三个消费点都从注册表取值：自动路由的可选清单、Executor 的必需小节、未填目标时的默认目标。启动时校验 code 唯一、GENERAL 存在、guidance 非空——写错的模式配置会让所有任务用错提纲，运行期极难发现，所以宁可拒绝启动。

历史数据的模式被下线后保留原始 code 展示，不改写成 GENERAL。

## 证据复用的前置条件

复用同一素材的历史证据能省掉转写与抽帧，但只有在「这份证据与当前配置等价」时才成立。说话人分离开关就是这样一个维度：开启分离后，旧任务留下的无标签转写必须重跑一次，否则讲者信息永久缺失；反过来，单人素材本来就不该有标签，不能把它当成「需要重跑」的理由。

判据因此落在**这份转写生成时有没有开分离**，而不是「转写里有没有 speaker 字段」。成功任务看报告 trace 里的 `speakerSeparation` 标记；断点续跑的任务还没有报告，标记随断点 payload 一起落库。两处都读不到时按未标记处理（宁可多跑一次），不按已标记处理。唯一的例外是断点续跑遇到旧数据：只要这份转写确实带着讲者标签，就认为它已经分离过——旧版本不写标记，标签是唯一可用的证据。
