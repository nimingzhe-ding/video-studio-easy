# 与参考项目 DOVideo-AI 的对比

本项目在立项时参考了 [DOVideo-AI](https://github.com/nimingzhe-ding/DOVideo-AI) 的产品思路与提示词设计。
两者解决的问题相近（把长视频变成可追溯的结构化知识），但**工程定位不同**，因此取舍也不同。

本文把差异写清楚，目的是让读代码的人知道：

- 哪些能力是刻意没做的，不是漏掉的；
- 哪些地方参考项目做得更深，值得借鉴；
- 真要往那个方向走，需要补什么。

> 对比基于参考项目的 `main` 分支（提交 `df4fa83`），数字为 `wc -l` 实测值。

---

## 1. 一句话定位

| | DOVideo-AI | 本项目 video-studio-easy |
| --- | --- | --- |
| 定位 | 长视频知识管理**平台** | 单机可跑的**文档生产工具** |
| 启动成本 | `docker-compose up` 起 6 个中间件 | `mvn spring-boot:run`，零外部依赖 |
| 面向 | 多用户、多素材、长期积累 | 一次导入、一份产出、随时追问 |

代码量几乎一样（9.8k vs 9.3k 行 Java），但**分布完全不同**：
参考项目大量代码用于基础设施接线（MyBatis-Plus、Redis、MinIO、RocketMQ、Qdrant），
本项目则集中在算法与流水线本身（音频切片、基频聚类、抽帧判重、证据校验）。

---

## 2. 规模与结构

| 指标 | DOVideo-AI | 本项目 |
| --- | --- | --- |
| 后端 Java 文件 / 行数 | 100 / 9,802 | 85 / 9,330 |
| 测试文件 / 用例 | 14 个测试文件 | 7 个文件、907 行、**42 个用例** |
| REST 端点 | 30 | 27 |
| 数据表 | 4（V1）+ 3 个增量迁移 | 10 |
| 提示词 | 硬编码在 `DeepSeekUtils.SYSTEM_POLICY` 与各 Service 字符串里 | 9 个独立 `.md` 文件，运行时加载 |
| 前端 | Vue + **Chrome 扩展**（29 个 JS/Vue 文件） | 纯 Vue（2,195 行） |
| 持久化 | MySQL + Redis + MinIO + Qdrant | H2 文件库 + 本地目录 |

关于测试分布的差异值得说明：
本项目的正确性风险在**算法**（音高聚类会不会把两个人并成一个、字幕时间轴会不会重叠、
校验器会不会放过编造的结论），所以单测集中在这些纯函数上；
参考项目的风险在**编排**（六个中间件之间的状态一致性），所以它的测试偏向集成路径。

## 3. 功能对照

### 3.1 两边都有

| 能力 | 说明 |
| --- | --- |
| 长音频转写 | 切片 → ASR → 按时间戳拼回 |
| 关键帧抽帧 + 画面文字识别 | ffmpeg 场景切分 + OCR |
| 时间戳证据链 | 每条结论必须能指回 `[mm:ss]` |
| 受控 Agent | Planner / Executor / Critic 三角色，最多 2 轮 |
| 确定性证据校验 | 不信任模型自评，逐条核对证据是否真的存在于原文 |
| 混合检索 | 语义 + 关键词 + 画面文字三路加权 |
| 自动模式判定 | 自然语言目标 → GENERAL / LEARNING / REVIEW / CREATION |
| SSE 实时进度 | 阶段事件流 |
| 分片上传 | 大文件断点续传 |
| 围绕报告追问 | 多轮对话，答案带时间戳 |

### 3.2 只有参考项目有

| 能力 | 实现方式 | 本项目为什么没做 |
| --- | --- | --- |
| **URL 直接导入** | `YtDlpUtils` 调 yt-dlp 抓 B站 / YouTube | 需要额外二进制 + 网络出口；demo 阶段先保证本地文件路径可靠 |
| **用户体系** | PBKDF2（210k 轮）+ Redis 会话 + 登录失败限流（8 次 / 10 分钟） | 单机单人使用，鉴权层只会增加配置负担 |
| **向量库** | `QdrantVectorStore`，**带降级**：检索失败时回落本地余弦，并上报 `vectorStoreFallbacks` 指标 | 单视频分块量级在几百，暴力检索毫秒级（见第 5 节数据） |
| **Agent 断点续跑** | `AgentCheckpointService` 把 `AgentState` 双写 Redis + DB，重启后从中断轮次继续 | 分析任务本身只有几十秒到几分钟，重跑成本低于维护 checkpoint 的一致性 |
| **成本预算** | `agent.budget.max-estimated-cost`，每轮检查 `usage.estimatedCost()`，超支即终止 | 只限制了轮次与时长；接入计费模型后才能定义「一轮多少钱」 |
| **难度分级队列** | RocketMQ 分发分析阶段 | 固定 2 线程池 + 数据库状态机已够单机用 |
| **Chrome 扩展** | 浏览器里一键提交当前页视频 | 需要配套的登录态与 URL 导入 |

其中**向量库的降级设计**特别值得记一笔：它不是「有 Qdrant 就依赖 Qdrant」，
而是把向量检索当成**可选加速**，失败时退回全量余弦，靠一个计数器暴露降级频率。
这个思路比单纯的「抽个接口以后换库」更实在。

### 3.3 只有本项目有

| 能力 | 说明 | 为什么参考项目没有 |
| --- | --- | --- |
| **说话人分离** | 纯本地：25ms 帧估基频（自相关 + 倍频保护）→ 一维层次聚类 → 回填「讲者 A/B」，报告、字幕、上下文全部带讲者 | 在参考项目里 `grep -rn "speaker\|diariz"` 零命中，`speaker` 字段不存在 |
| **Word 报告** | Apache POI 生成 `.docx`，在「视频证据」之后按时间插入关键帧截图，支持表格/引用/有序列表/行内粗体 | `grep -rn "XWPF\|docx"` 零命中，产出只有网页 Markdown |
| **字幕导出** | SRT / VTT / TXT，带讲者前缀，自动处理重叠与零长度 | 无 |
| **定向视觉描述** | 只对「OCR 一个字都没读到」的帧调用视觉模型写一句描述，默认关闭、按配额限量，且描述本身要能通过逐字校验 | 参考项目同样只做 OCR，且在其 `docs/interview-qa-v2.md` Q8 明确表示「视频模型应对低置信度或强视觉任务定向调用，而不是所有关键帧全量调用」——本项目把这个立场落成了开关 |

一句话概括：**参考项目的强项在「接得多」，本项目的强项在「出得去」**。
一份能发给别人看的 Word、一份能拖进剪辑软件的字幕，是它没有覆盖的最后一公里。

## 4. 同一件事的不同做法

### 4.1 检索粒度：chunk 级 vs 两段式

| | DOVideo-AI | 本项目 |
| --- | --- | --- |
| 粗排 | chunk 打分 | chunk 打分 |
| 细排 | **对 chunk 内每个 segment 再打分**，权重 `chunk*0.55 + 转写*0.25 + 画面*0.20` | 无，直接取 Top-K 整个 chunk |
| 返回 | segment 级命中（更精确） | chunk 级命中，内部片段整体交给 Agent |

参考项目的做法更精细：一个 5 分钟分块里可能只有 20 秒是真正相关的，
两段式能把那 20 秒单独拎出来喂给模型，上下文利用率更高。
本项目选择 chunk 级，是因为报告的结论本来就以分块为单位组织，再细一层的收益不明显。

### 4.2 上下文预算

两边都受字符上限约束，但策略不同：

- 参考项目：逐条累加字符，**超预算就跳过该条继续尝试后面的**（后面的条目可能更短）。
- 本项目：同样的「逐条选入、超了 `continue` 而非 `break`」，但额外做了两件事：
  多轮补证时把预算放大 1.5 倍（`budgetScale`），以及末尾只在超过 5% 时才按换行兜底截断，
  避免把一句话切成两半。

### 4.3 提示词的组织

- 参考项目：`SYSTEM_POLICY` 常量 + 各 Service 内联字符串拼接。
- 本项目：`server/src/main/resources/prompts/` 下 9 个 `.md` 文件，由 `PromptLibrary` 运行时读取并缓存。

拆成文件的直接好处是改措辞不用重新编译，且 `docs/prompts.md` 可以逐条解释为什么这么写。
代价是多一次 IO（已被缓存吸收）。

### 4.4 失败处理

| 场景 | DOVideo-AI | 本项目 |
| --- | --- | --- |
| 向量检索失败 | 降级为本地余弦 + 上报指标 | 本来就只有本地余弦 |
| Agent 中断 | 从 checkpoint 恢复 | 任务标记失败，可一键「换个目标重跑」或复用证据重跑 |
| 大模型未配置 | 无法运行 | **离线确定性模板**，全流程可跑通 |

最后一行是本项目最实用的一个设计：没有 API key 时，
报告会由模板根据真实转写与画面文字拼出来，标点与措辞不如模型，但证据链是完整的。

## 5. 内存与向量库的实测数据

「为什么不接向量库」这件事，用数字回答比用形容词可靠。
用 `ContextChunk` 的真实结构（含 1024 维向量）做写入 + 读取 + 检索的探针：

| 分块数 | 对应素材时长 | 写入 | 读取并解析 JSON | 堆增长 |
| --- | --- | --- | --- | --- |
| 24 | 2 小时 | 19 ms | 32 ms | ~0 MB |
| 120 | 10 小时 | 21 ms | 21 ms | 4.5 MB |
| 600 | 50 小时 | 49 ms | 49 ms | 22.4 MB |
| 2000 | 166 小时 | 144 ms | 118 ms | 73.1 MB |

同一探针还暴露出两处**已知浪费**（当前规模下不影响产品表现，记录下来备查）：

| 项目 | 现状 | 更优做法 | 倍数 |
| --- | --- | --- | --- |
| 向量表示 | `List<Double>` 装箱，38 KB/条 | `double[]`，8 KB/条 | **4.7×** |
| 向量存储 | JSON 文本列，6506 字节 | 二进制列，4096 字节 | **1.6×** |

结论：**单素材分析场景下内存方案完全够用**（5 分钟一块，10 小时课程也只有 120 块、4.5 MB）。
真正需要向量库的分界线是「查询是否跨任务」——
如果是「在我的所有视频里搜这句话」，那就得换成外部索引，把读的量从 O(n) 降到 O(k)。

## 6. 若要补齐差距，各需要什么

按投入产出排序（都是「如果要做」的备忘，不是待办）：

| 补齐项 | 工作量 | 代价 |
| --- | --- | --- |
| 向量库（Qdrant） | 中：加 `VectorIndex` 接口 + 一个实现 + 降级路径 | 多一个必须部署的服务，「clone 下来就能跑」这条路径会断 |
| pgvector 折中方案 | 中：用 Postgres 替换 H2 | 向量与业务数据同库同备份，但本地开发需要 Postgres |
| 登录 | 小到中：PBKDF2 + 会话 + 拦截器 | 单机场景纯负担，除非要多人共用 |
| URL 导入 | 小：接 yt-dlp + 一个下载阶段 | 需要额外二进制与网络出口，且要处理平台反爬 |
| Agent checkpoint | 中：状态序列化 + 恢复入口 | 分析本身只有几十秒，重跑比恢复更简单 |
| 成本预算 | 小：按 token 数 × 单价估算 | 需要先定义「一轮多少钱」，否则阈值是拍脑袋 |

## 7. 一句话总结

参考项目证明了一件事：**把长视频拆成带时间戳的证据，再用受控 Agent 组织成结论**，
这条路是可行的，而且产品价值确实在证据链上。

本项目沿用了它的骨架（提示词、校验规则、打分权重、模式划分），
砍掉了 demo 阶段不必要的中间件，把省下的复杂度投到了两处它没覆盖的地方：
**算法侧的说话人分离**，和**产出侧的 Word / 字幕**。

真要说谁更好，取决于用途：
要多人协作、多素材沉淀、可长期检索，选参考项目那套；
要一个人把一个视频快速变成一份能交出去的文档，本项目的路径更短。
